# 强化符文（军略）系统设计方案

> 整理日期：2026-11-01
> 参考对象：《金铲铲之战》海克斯强化（Augment）
> 定位：局内构筑变量，补足“每局不一样”的随机性
> 相关文档：[AI选牌与买卖策略](./AI选牌与买卖策略.md)、[职业与兵种连锁配置](./职业与兵种连锁配置.md)、[好友羁绊与武将分组](./好友羁绊与武将分组.md)、[卡牌属性体系重构方案](./done%20卡牌属性体系重构方案.md)

## 一、系统定位

金铲铲的强化符文是“**每局 3 次、三选一、整局生效**”的随机强力增益，是仅次于羁绊的第二构筑维度。本方案把它落到三国题材下，暂名**军略**，但对外仍可叫“强化符文”。

它必须满足三点：

1. **不占装备、不占羁绊位**：独立一层，避免与现有 89 件道具、19 个职业、32 个好友组冲突。
2. **能改变决策，而不只是加数值**：经济类、商店类、羁绊类、规则类都要有，纯数值类只占一半。
3. **AI 也要选**：否则人类玩家单方面变强，8 人局平衡崩掉。

---

## 二、规则框架

| 项目 | 建议 |
| --- | --- |
| 出现次数 | 每局 3 次 |
| 出现时机 | 第 2、10、20 回合的商店阶段（与许愿 10/25/40 错开，第一次让玩家在开局就定型） |
| 选择方式 | 三选一，不可跳过；每局可“换一批”1 次 |
| 稀有度 | 银（普通）/ 金（稀有）/ 棱彩（传说），权重约 60% / 30% / 10%，越晚越偏金彩 |
| 重复保护 | 同一符文整局只出现一次；同 Id 不可叠加 |
| 生效范围 | 选完立即生效，持续整局；读档后重新应用 |
| 与其他系统 | 不可出售、不可替换、不占卡位/装备槽 |
| AI 处理 | 每个 AI 按自身 `PlayerConfig` 性格（经济型/战斗型/羁绊型）独立评分选择 |

**卡池与条件**：部分符文带前置条件（指定地图规则、指定职业已有 2 人、PVE 回合等），条件不满足时不进入候选池，避免“选了个用不上的”。

**数值叠加约定**：

- 同一 key 的增益**加算**（如两个“全队攻击 +8%”= +16%），不同 key **乘算**；
- 单 key 总加成设上限（攻击/法强 ≤ +40%，减伤 ≤ 25%，攻速 ≤ +50%）；
- 所有“百分比”都基于 1 星面板，避免与 5 级卡 × 品质 × 星级倍率形成指数爆炸。

## 四、与现有系统的耦合与风险

1. **不要改配置类之外的“硬编码上限”**：装备槽 3、上阵格 9、卡上限 15、士兵每行 5、许愿槽 3 目前都分散在 `GameConst`、`PlayerInfo`、`CombatConst` 与商店代码里。做符文前先把这些改成“基础值 + 修正值”，否则符文只能做纯数值。
2. **属性修正要区分“快照”与“实时”**：现有 `JobLinkManager` 在开战时算一次并乘入生命基准，`FactionShieldManager` 也在开战时施加。符文若要求“战斗中动态生效”（如背水、乘胜、神速），必须走 Buff 或事件，不能塞进开战快照。
3. **许愿/点赞/代友道具**是三个不同的“出卡权重/羁绊人数”入口，容易互相叠加，建议统一由 `HeroSelectionTool` 与 `FriendLineManager` 汇总，符文只提供倍率，不直接改内部字段。
4. **存档**：`PlayerInfo` 增加 `augmentIds` 列表并在 `Serialize/Deserialize` 往返；读档时对静态类符文重新应用（经济/商店/羁绊），战斗类符文每场重置。
5. **AI**：在 `AIConst` 增加三类性格权重（经济、战斗、羁绊），AI 对候选符文打分；不要让 AI 选“地图条件符文”而当前不是该地图。

## 五、实现落点

- **配置**：新增 `Assets/Resources/Scripts/Configs/AugmentConfig_s.cs`，字段建议 `Id / Name / Des / Rarity / Category / Effect / Value / StartRound / Weight / Tags / Repeatable`。`Effect` 采用与 `SkillConfig`、`ItemConfig` 一致的 `key:value,key:value` 串，不写死在代码里。
- **回合表**：`GameRoundConfig_s.cs` 新增一列“强化符文档位”（0=不出现，1/2/3=本次三选一的最高稀有度），由数据决定第几回合出、出什么池。
- **管理器**：新增 `Combat/AugmentManager.cs`（静态类），提供 `RollChoices(pid, tier)`、`Apply(pid, augmentId)`、`GetModifier(pid, key, baseValue)`。经济/商店类读 `GetModifier`，战斗类在 `WorldManager.BattleBegin` 统一施加。
- **UI**：`PanelManager` 新增 `ShowAugment()` 三选一面板，在商店阶段开始前弹出，选择后回到原商店流程；商店面板与背包不感知符文细节。
- **注册**：`ConfigManager.Init()` 注册 `AugmentConfig.Load()`；`.csproj` 补 `<Compile Include>`。

## 六、首版建议范围（MVP）

先做 **24 条**，只做“改数值 + 复用现有 Buff”，不做新机制、不做地图条件符文：

- 经济 8：屯田、募资、善贾、省用、轻徭、加官、连胜赏、连败恤
- 商店 4：求贤令、点将、开市、许愿
- 羁绊 4：同袍、帅旗、军令、宗亲（阵营档位 -1）
- 战斗 8：破军、铁壁、法正、疾风、血战、空城、回春、龟缩

这三类能覆盖“攒钱、刷卡、凑羁绊、拼战斗”四条主线，验证“符文是否真的改变了每局的决策”后，再上机制类和棱彩类。

## 七、刻意不做的部分

- **不做“复制装备/复制英雄”类**：会直接放大现有 5 级卡与 89 件道具的滚雪球，且与卡上限 15、装备槽 3 冲突。
- **不做“每回合免费刷新无限次”**：共享商店有 15 张卡池轮转，无限刷新会抽干卡池并破坏 8 人顺序博弈。
- **不做“直接送羁绊人数”**（如凭空 +2 同职业）：应通过“虚拟人数 +1”实现，避免绕过上阵格与阵容构筑。
- **不做纯运气型符文**（如“战斗开始随机秒杀一人”）：AI 无法评估，胜率方差过大。
